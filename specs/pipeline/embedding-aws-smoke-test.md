# Embedding AWSスモークテスト

Status: 起動確認専用のaws-smoke-upを追加。旧構成の削除・残存確認は完了済み。新しい起動経路の実AWS検証とEmbedding試験は未実行。


## 今回実装した範囲

`infra/aws-test/bootstrap/`に常設基盤、`infra/aws-test/smoke/`に試験用設備を分離した。
対象はローカル設定に登録したテスト専用アカウント、東京リージョン。通信・IAM・秘密値登録・plan・削除候補の確認手順は[テストAWS環境のREADME](../../infra/aws-test/README.md)を参照する。
初回保存・再配送の試験コードとRunnerからのSSM呼出に、DB準備・結果回収・自動削除の実行コマンドを接続した。今回の完了条件は静的検証までとし、実AWSの試験設備の起動・試験・削除結果は初回実行で確認する。実行手順は[README](../../infra/aws-test/README.md#実行コマンドの使い方)を参照する。
起動確認専用の`up`はsmallのEC2とSSM専用経路を使い、環境を保持して終了する。AWSへ接続しない単体・モックテストで検証し、実AWSの受入確認は別途実施する。

## 運用者のアクセス権限

テスト用ユーザーへ`VectorTestManager`と`VectorTestRunner`を割り当て、設備管理と試験実行でセッションを使い分ける。
Managerは既存のTerraform構築ロールを引き受けて設備を作成・削除し、テストECRへの配布とENI削除待機の照会も担当する。RunnerはSSMでrunner EC2へ試験を投入し、終了状態とテストログを取得する。
bootstrapは既存管理者の`WorkloadAdministrator`で運用し、その権限の細分化は別途扱う。テストアカウントに`VectorDeploy`や独立したReadOnlyの割当は追加しない。
インラインポリシーと利用開始前の信頼先・プロファイル設定は[アクセス権限](../../infra/aws-test/ACCESS.md)を正本とする。ユーザーの割当だけでsmokeの実行準備が完了したとは扱わない。

## Problem

ローカルで確認したEmbedding処理を、本番へ出すイメージでAWS上でも動かし、実SQS配信・Lambda起動・IAM認証・SSM取得・外部AI通信・RDS保存の接続を確認する。
本番とは別のAWSアカウントに必要時だけ試験環境を構築し、結果を回収して削除する。

## Evidence

- `backend/local_tests/embedding/`: migration適用済みDBを使った保存・失敗・接続解放・重複配送・同時処理のテスト。
- `backend/local_tests/database.py`: ロール・Better Auth・Alembicを用いたDB準備の既存実装。
- `backend/app/lambda_handlers/embedding/`: 実ハンドラー、設定、IAM接続とSSM取得。
- `infra/aws/embedding_consumer.tf`: 本番のLambda・IAM・SQSイベントソースマッピング。
- `infra/aws/outbox_relay.tf`: キューと再配送設定。
- `infra/aws/proxy.tf`と`infra/aws/templates/squid.conf.tftpl`: 本番の外向きプロキシ構成。
- `infra/aws/scripts/verify-embedding-runtime.py`: リソースを差し替えるイメージ内起動試験であり、実AWS接続の保証ではない。

既存Terraformは構成の参考とし、本番のstateや実行リソースをテストから操作しない。
追加済みのローカルテストにはユーザー指示による未実行分があり、追加したことだけでローカル合格とは扱わない。

## Invariants

- テスト専用AWSアカウントを使用し、本番のDB・キュー・Lambda・ネットワーク・IAM実行ロール・SSM・AIキー・ログを共有しない。
- Terraformの構成とstateを本番から分離し、構築・試験・削除の開始前に実行先アカウントIDを照合する。
- 本番へ出すものと同一内容のイメージをテスト用ECRへコピーし、タグだけでなくdigestとソースrevisionを記録する；テスト向けの製品コード差し替えはしない。
- DB構造・ロールは既存の正本から適用し、試験を通すための追加GRANT、IAM認証の迂回、`create_all`や`stamp`による代替は行わない。
- 本番の実行権限の意図を保ち、リソース参照先をテストアカウントに限定する。
- Lambdaは実アプリ用DBロールを使用し、準備用の管理権限を持たせない。
- 外部AIは実通信し、記事データとキーはテスト専用のものを使う。
- `.env`を利用せず、秘密値をTerraform変数・state・出力・試験レポートへ書かない。
- 必須の確認不能・期限切れは合格にせず、試験失敗と環境削除失敗を別々に記録する。

## 構成

| リソース | 用途・方針 |
|---|---|
| Lambda | 実Embeddingハンドラーを検証対象のイメージで起動する |
| SQS・イベントソースマッピング | 実配信でLambdaを起動する；初期値は本番同様1回1件・ReportBatchItemFailures |
| RDS PostgreSQL | 小規模なSingle-AZ構成、外部公開なし、IAM DB認証有効 |
| VPC・サブネット・セキュリティグループ | LambdaとRDSをプライベート側へ置き、DB接続元を必要なリソースに限定する |
| プロキシEC2 | 外部AIへの通信経路；NAT Gatewayは作成せず、テスト内部からの利用に限定する |
| テスト実行用EC2 | DB準備・イベント投入・処理待機・保存結果の照合・結果出力を担当する |
| IAM | Lambda・プロキシ・テスト実行用EC2の責務に応じた専用ロールを用意する |
| SSM Parameter Store | テスト専用AIキーなどを格納し、本番の値は参照しない |
| CloudWatch Logs | Lambdaとテスト実行の詳細ログを確認する |
| テスト用ECR | 同一内容の検証対象イメージを保持する |

RDSはSingle-AZでも、DBサブネットグループ等のAWS要件を満たすサブネットを用意する。
DBの容量・冗長化・同時実行規模は本番と同一にする必要はない。
イメージのコピーは配布工程だけで行い、試験実行中に本番リソースへのアクセスを必要としない。

### 通信経路

- LambdaからRDS、テスト実行用EC2からRDSはVPC内で接続する。
- 外部AIへのHTTPS通信はテスト専用プロキシを経由する。
- プロキシは外向き接続が可能な側に配置し、外部から利用可能な公開プロキシにしない。
- LambdaのSSM取得、EC2の管理、SQS投入、ECR取得、ログ出力に必要なAWSサービスへの経路も定義する。
- アカウント分離だけでは通信経路は成立しない；SDKとSSM Agentのプロキシ設定、必要な許可先、VPCエンドポイントの要否を実装前に確定する。
- Lambdaをパブリックサブネットへ置くだけで外部通信できる構成とは扱わない。

SSM AgentにはHTTPプロキシ設定があるが、製品SDKが同じ設定を使うとは仮定しない。
既存実装にはプロキシ設定を明示的に無効化するAWSクライアントもあるため、各クライアントと通信先を照合する。

## テスト実行用EC2の責務

1. テストRDSへ必要な初期ロール・拡張・Better Auth管理スキーマ・Alembic migrationを既存の正本に従って適用する。
2. Alembic headへの到達と、試験に必要な初期データ・アプリロールの成立を確認する。
3. 実行IDで識別できる生成可能な分析済み記事を作る。
4. 実イベント契約に従うメッセージをテストSQSへ投入する。
5. 期限付きで対象イベントの完了を待ち、別DB接続から保存結果を確認する。
6. 各確認の合否と失敗理由を出力し、実行元へ結果を返す。

準備用の管理接続と結果確認用の接続を区別し、管理接続の成功をLambdaのアプリ権限での保存成功の代替にしない。
EC2の操作はSSM Run Commandを第一候補とし、結果取得は手元またはCIから行う。
Terraformはインフラを管理し、migration・データ準備・試験の実行は専用スクリプトで行う。

## 初回に実装する試験

[AWSテスト](../../backend/aws_tests/README.md)に初回保存と再配送の2ケースを用意する。各ケースは独立した記事を準備し、再配送ケースは初回保存も含む。以下を合格条件とする。

- 検証対象digestのLambdaが、投入したイベントを処理したことを実行ID・イベントID・分析記事IDで関連付けられる。
- 処理が保存成功として完了し、初期化失敗やメッセージ処理失敗になっていない。
- 別DB接続で対象記事のEmbeddingが確定保存され、製品契約の次元数・有限値を満たす。
- 再配送では同じ本文を再投入し、新しいSQS message IDの`already_embedded`完了を確認してから、初回保存したベクトルと完全一致することを確認する。
- キューの概算件数は診断情報とし、保存・再配送成功の判定には使わない。
- 必要な結果を実行元へ回収できる。

実AIの応答値を固定ベクトルとは比較しない。
接続が成立したことだけでなく、アプリ用DBロールで確定保存されたことまで確認する。

### 後続の試験

- 失敗時の配信: 専用DLQとredrive設定を用意し、失敗イベントの再配送と受信上限後のDLQ移動を確認する。
- 可視性タイムアウトと待機期限の関係を定義し、短縮する場合は本番との差分を試験結果に残す。

同時処理・ロールバック・接続解放・エラー分類の細かなケースをAWSで再網羅しない。
Outbox relayからの送信は初回の範囲に含めず、SQSへの投入を試験入口とする。

## 試験結果と削除

S3は初回の結果保存先として必須にしない。

### 自動実行と試験期限

一括実行`aws-smoke`は1回のコマンドで「構築 → 起動確認 → DB準備 → 試験 → 結果回収 → 削除 → 残存確認」を実行する。以下の自動削除規則は一括実行に適用し、環境を保持する`up`・`prepare`・`test`には適用しない。

- AWS操作前にコピーしたテストの収集を60秒以内で確認し、0件・収集エラー・収集時skipは拒否する。
- pytest起動からsetup・call・teardown全体で`TIMEOUT`（正の整数秒、既定300秒）を共有し、Embedding runtimeにも同じ期限を渡す。
- 期限内に確認が終わらなければタイムアウト失敗を記録し、既存のプロセス終了処理へ進む。投入済みSSM・Lambdaの即時停止は保証しない。
- 構築・DB準備・結果回収・削除にも、それぞれ有限の待機期限を設ける；試験期限で構築や削除を途中停止しない。
- 構築途中の失敗、DB準備失敗、試験失敗、通常の中断でも、作成済みの試験リソースを削除する処理を実行する。
- 結果回収には期限を設け、回収失敗が削除開始を無期限に妨げないようにする。
- 試験期限には起動確認・ログ回収・プロセス終了待ち・削除時間を含めず、環境全体の稼働時間や削除完了時刻の保証とは扱わない。

最初は実行元のスクリプトでこの流れを制御する。
実行元の電源断・強制終了・認証失効などでは自動削除が完了しない可能性があるため、独立した手動削除と残存確認を用意する。
実行元から独立したAWS側の期限切れ削除は初回実装に含めず、電源断時も削除できる保証とは扱わない。

### コマンドの契約

以下のコマンドを実装する。実AWSでの成否は初回実行まで未確認。

| コマンド | 責務 |
|---|---|
| `make aws-smoke-up RUN_ID=<実行ID>` | 構築・EC2起動・SSMコマンド・プロキシ経由ECRの確認まで行い、環境を保持する |
| `make aws-smoke-prepare RUN_ID=<実行ID>` | 起動済み環境に準備ファイル・固定イメージ・DBを準備し、実状態を確認して環境を保持する |
| `make aws-smoke-test RUN_ID=<実行ID> TEST=aws_tests/embedding/` | 準備済み環境で指定対象を実行し、コードと結果を保存して環境を保持する |
| `make aws-smoke TEST=aws_tests/embedding/` | 一連の構築・準備・指定対象の試験・結果回収・削除・残存確認を実行する |
| `make aws-smoke-destroy RUN_ID=<実行ID>` | 指定した試験環境だけを削除し、残存確認まで行う；失敗後も再実行できる |
| `make aws-smoke-status RUN_ID=<実行ID>` | 保存済みレポートを表示し、AWSを読み取りで照合して残存・確認不能を報告する |

各操作はテストアカウントと試験専用stateを照合し、常設基盤のstateへ削除を実行しない。
削除が途中で失敗してもstateと実行情報を残し、同じ実行IDで再試行できるようにする。
試験成功と削除成功を別々に記録し、どちらかの失敗を正常な終了コードで隠さない。
認証が使えなくても、手元に回収済みのレポートは読めるようにする；最新のAWS残存確認は別途認証を必要とする。

### 起動確認専用コマンド

`up`は既存Terraform構成全体を作成する。DB準備・認証schema生成・イベント投入・AI呼出は行わない。両EC2は`t4g.small`、SSM Agentの通信はssm/ssmmessagesのInterface endpointを使用し、runnerのプロキシ依存から分離する。RunnerのSSMコマンド実行権限はrunner EC2だけに維持する。

構築完了を保存してから実リソース・digestの照合と起動確認へ進む。両EC2のステータスチェックとSSM Online、runnerへの固有の応答、bootstrap ready・Docker稼働、プロキシTCP接続、プロキシ経由ECRでの指定digest取得を必須とする。起動確認は合計900秒を上限にし、API通信にも期限を設ける。管理確認のSSM出力はCloudWatchへ転送せず直接取得する。

同じIDの再実行では、構築前失敗は再試行、構築完了済みは再applyなしで再確認する。構築途中の完了不明や削除開始済みの環境を自動再構築しない。入力・所有者不一致、並行操作は拒否する。最新の合否と各回の状態・Command IDを保存し、過去の成功を今回の合格として扱わない。

成功・失敗・通常の中断でも環境を保持し、結果保存先と`aws-smoke-destroy`を表示する。構築開始後の失敗時は期限付きのログ回収を試みる。DB準備・試験の未実行を維持し、起動確認の合格判定から除外する。具体的な手順と再実行条件は[README](../../infra/aws-test/README.md#起動確認だけを実行する)に従う。

### DB準備専用コマンド

`prepare`は既存RUN_IDの構築・`up`成功を要求し、削除開始済みの環境を拒否する。保存済み設定・実行主体・所有者・実リソースを照合して現在の起動・SSM・プロキシ疎通を再確認する。Terraform apply、試験イベント投入、AI呼出、自動削除は行わない。

準備ファイル生成・固定backend digest取得・DB準備を個別に記録する。完成済みファイルはsource revisionとハッシュが一致する場合だけ、イメージは固定digestを確認できる場合だけ再利用する。空のDBには初期設定SQL・認証DDL・Alembicを適用し、準備済みDBは読み取り確認だけを行う。不完全なDBや異なるrevisionを自動修復・再初期化しない。

合格にはDB内のrevisionとイメージのmigration head一致、pgvector・必要な認証テーブル・参照データの存在、`vector_app`のIAM認証・TLS接続でのEmbedding対象テーブル読み取りを要求する。専用の非待機session advisory lockを準備全体で保持し、既存migrationロックとは別キーにする。工程結果・安全な失敗理由・SSM Command ID・再実行履歴を保存し、前回の成功を今回の合格に流用しない。

一括実行も同じ準備処理を使用し、既存の終了後削除を維持する。今回の検証はprepare専用ユニットテスト・ローカルDBテスト、既存のup境界と一括終了処理の2ケース、変更ファイルの静的チェックに限定する。RDS・IAM・TLS・SSMの実AWS確認とEmbedding正常系は後続工程とする。手順は[README](../../infra/aws-test/README.md#起動済み環境のdb準備を実行する)を参照。

### 対象を指定する試験専用コマンド

`test`は構築・`up`・`prepare`の成功した既存RUN_IDを要求する。保存済み入力・所有者・実行主体・リソースを照合し、起動・SSM・プロキシ疎通を再確認する。未準備・削除開始済み・同一RUN_IDの並行操作を拒否する。Terraform apply、DB再初期化、イメージ変更を行わず、成功・失敗・通常の中断とも環境を保持して再実行・削除コマンドを表示する。

`TEST`は`backend/aws_tests`内のディレクトリ・ファイル・pytest node IDを1つ受け付ける。指定漏れ・不存在・範囲外・オプション指定は拒否し、一括実行にも指定を必須とする。必要な設備は既存環境に用意されていることを前提とし、任意のテストに合わせた設備追加は行わない。

実行時点のテスト・conftest・補助コード・fixtureファイルを、未コミット変更・追加も含めて`test-attempts/<連番>/code/`へコピーして実行する。隠しファイル（`.env`を含む）・キャッシュ・ログ・範囲外へ向くシンボリックリンクは取り込まない。実行中の元コード編集を混入させず、次回に反映する。アプリイメージと環境revision・起動時の定義ハッシュは固定したまま、テスト側Git revision・ファイルハッシュを別に残す。

各回へ対象・収集node ID・期限・時刻・終了コード・ケース別JSON・JUnit・pytestログ・コードを保存し、過去の実行を上書きしない。未開始・実行中・成功・失敗・skipを区別して逐次保存し、1件以上の収集対象すべてが完了・成功し、pytest終了コードが0の場合だけ合格とする。skip・xfail・未完了は合格に含めない。中断でJUnitが完成しなくてもJSONとログを保持する。

CloudWatchログは成功・失敗とも期限付きで回収して各回へ関連付ける。回収成否はケース成否と別に記録し、回収失敗はコマンド全体の非0終了とする。最新結果を既存サマリーに反映する。一括実行も同じ試験処理を使い、終了後削除を維持する。

この実行制御の検証はAWSへ接続しない専用テスト、影響する既存のup・prepare・一括削除・プロセス終了のケース、変更PythonのRuff・formatと`git diff --check`に限定する。実AWS・実AI・DB・Terraform・backend/frontend全体のテストはこの変更で実行しない。[操作と保存先](../../infra/aws-test/README.md#準備済み環境で対象を指定して試験する)を参照する。

### 削除専用コマンド

`destroy`は構築applyを開始した既存RUN_IDを受け付け、起動・準備・試験の成功を要求しない。構築未開始は拒否する。保存済み定義・入力のハッシュ、Managerの実行主体・期待アカウント、所有記録、試験専用bucketとstate keyを照合してからログ回収・削除へ進む。同じRUN_IDへの並行操作と対象不一致を拒否する。

ログはRunnerの実行主体を確認して120秒を上限に回収する。不存在のグループは`absent`、認証・権限・通信・期限切れは回収失敗とする。回収に失敗してもManagerによる削除は続行し、削除完了を`deletion_status`、回収を含む全体の成否を`status`へ別記して非0終了する。一括実行は同じ呼出内の回収結果と保存先を渡し、二重に回収しない。

固定したTerraform定義で全体destroyを行い、部分削除・stateロックの強制解除・IDによる直接削除は追加しない。既存のdestroy apply90分・残存再照会180秒を維持し、工程・経過時間と取得できる残存件数を表示する。中断後は結果と設定を保持し、同じコマンドで再試行する。ローカル中断をAWS側の即時停止とは扱わない。

stateが空で、AWS照会でも対象設備が残っていない場合だけ削除完了とする。削除前照会の失敗でも削除を試みるが、確認不能を削除完了にはしない。既知のリソースIDをstate・最新照会と統合して保持し、空の照会結果で失わないようにする。再実行時にstateが空ならapplyを省略して残存確認する。残存があれば期限内で再照会し、残存・照会不能は非0終了する。過去の回収失敗は履歴に保持し、今回の成功を妨げない。

`destroy-attempts/<連番>/`へ各回の工程状態・時刻・失敗理由・回収結果・Terraformログとplan・削除前後の照会結果を保存する。最新結果と保存先を既存サマリーへ反映し、過去の削除履歴・試験合否・コード・固定設定は変更しない。旧形式の実行記録も受け付ける。常設IAM・ECR・state基盤・SSM設定は保持する。

検証はAWSに接続しない削除専用テストと影響する既存ケース、変更PythonのRuff・format確認、`git diff --check`に限定する。実AWS・実AI・DB・Terraform・backend/frontend一式は実行しない。実際の削除時間、IAM権限、ENI解放、AWS残存確認は後続のAWS実行で検証する。[操作と保存先](../../infra/aws-test/README.md#試験環境を片付ける)を参照する。

### 削除後に残すレポート

実行ごとに手元のGit管理外ディレクトリへ`result.json`と読みやすい`summary.txt`、必要なログを保存する。
実行開始時に実行IDと確認済みアカウント・リージョン・stateの識別情報を保存し、工程ごとに更新する。
長期保管用サービスや専用画面は追加せず、まずファイルだけで削除後も状況を確認できるようにする。

レポートには少なくとも次を残す。

- 構築・DB準備・試験・結果回収・削除・残存確認それぞれの状態、開始終了時刻、失敗理由。
- イメージdigest・ソースrevision・migration revisionと、イベント・記事の識別子。
- 試験の各確認項目の合否；未実行・タイムアウト・確認不能は成功と区別する。
- 削除後に残った試験リソースの種別・識別子、または残存なしという確認結果。
- 常設するstate用S3・IAM・ECR・SSMは意図して残すものとして別記する。

Terraformの削除成功に加え、実行中に記録したリソースIDと実行IDタグを使ってAWSの状態を読み取り確認する。
RDS・EC2・EBS・IP・VPCエンドポイントなどの試験リソースについて、削除中・残存・確認不能を削除完了と混同しない。
手動削除の再実行後にもレポートを更新し、元の試験結果は維持する。

| 内容 | 保存先 |
|---|---|
| 合否、確認項目、失敗理由、実行時刻、アカウント・リージョン、実行ID、イベント・記事ID、revision・digest・migration revision | 手元のレポート、またはCI成果物 |
| Lambda・テスト実行の詳細ログ | テストアカウントのCloudWatch Logs；削除前に必要分を実行元へ回収する |
| 長期保管レポート | 必要になった段階でS3を検討する |

一括実行は結果回収を成功・失敗のどちらでも試み、その後に試験環境を削除する。
一括実行は結果取得に失敗しても削除へ進み、取得失敗と削除結果を実行元に記録する。個別実行は環境を保持し、利用者が明示的に削除する。
RDS・EC2・プロキシ・関連ストレージ・IP・キュー・ネットワーク等の残存を確認し、削除失敗を見える形で返す。
テストDBのデータ保存は目的ではないため、通常の試験終了時はDBスナップショットを残さない。

AWSアカウント・アクセス設定・Terraform stateの基盤は試験ごとの削除対象から分離する。
ECRイメージ・SSMの秘密値・ログの保持期間と削除単位は、実装時に明示する。
Terraform stateの保存先と試験結果の保存先は別の責務であり、結果用S3を作らないことはstate用S3の利用を禁止する意味ではない。

## Non-goals

- 本番環境の複製、本番アカウントや本番データを使う試験。
- 全工程・負荷・性能・高可用性・障害復旧の網羅。
- 常設のRDS、NAT Gateway、本番と同規模のネットワーク設備。
- 初回からのDLQ試験、Outbox relay・Schedulerの構築、長期保管用S3。
- この仕様書作成に伴うAWSアカウント作成、インフラ適用、テスト実行。

## Done

実装の完了条件は、専用アカウントで構築・DB準備・正常系試験・結果回収・削除を一連の手順で実施でき、各工程の失敗を識別できることとする。
削除後に再構築して同じ手順が成立し、残存リソースの扱いが明確であることを確認する。
正常終了・試験タイムアウト・途中失敗の終了処理を検証し、削除後に手元の結果を読めることと、手動削除・残存確認を再実行できることを確認する。
次工程へ進む条件は「対象revisionのローカルテスト合格 → 同一イメージのAWS試験合格」とし、未実行を合格と記録しない。
今回の起動コマンドは単体・モックテストで検証する。実AWSでは新規up、同じIDでの再確認、プロキシ経路障害中のSSM疎通、復旧後の削除と残存0件を受入条件とし、実行を指示された段階で確認する。

## 着手順序

1. ユーザーがテスト専用AWSアカウントを作成する。
2. アカウントID、使用リージョン、作業用ロール・SSO等のアクセス方法を確認する；秘密キーは会話に貼らない。
3. テスト専用Terraformの配置・state、通信経路、イメージ配布、秘密値の登録・保持方法を確定する。
4. 基盤とテスト実行用EC2を実装し、DB準備から正常系試験・結果回収・削除までを接続する。
5. テスト実行が許可された段階でローカル・AWSの順に検証する。
6. 重複配送、失敗時の再配送・DLQ試験を追加する。
