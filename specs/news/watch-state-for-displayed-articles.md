# 表示中の記事のウォッチ状態

Status: Implemented
工程: backend(schemas/watchlist.py ほか) → /gen-types → frontend → /check

## 目的

ウォッチ状態の問い合わせを、ウォッチ中の記事の全件ではなく、画面に出す記事の分だけにする。
レスポンスの大きさがウォッチ数ではなく表示件数で決まるようにし、「さらに読み込む」で足した記事にも正しいウォッチ状態を出す。

## API

`GET /api/v1/me/watchlist/ids?articleIds=1&articleIds=2`

- `articleIds` は必須で 1〜24件 (`ARTICLE_LIST_LIMIT`)。各要素は記事 ID と同じ範囲 (1〜int4 の上限)。欠落・件数外・範囲外は 422。
- レスポンスは `WatchlistIds { ids }` のまま。渡した記事のうち本人がウォッチ中のものの ID を、記事 ID の昇順で返す。存在しない記事 ID は含まれないだけで、エラーにしない。
- 認可はログイン (変えない)。

## 画面ごとの問い合わせ

| 画面 | 問い合わせ |
|---|---|
| ダッシュボード | 最初の24件を取ってから、その ID で1回。「さらに読み込む」では `loadMoreArticles` が、足した記事と一緒にそのウォッチ状態を返す |
| 記事詳細 | 本文の記事は URL の ID で、記事・関連記事の取得と同時に1回。関連記事は、取得後にその ID で1回 |
| ウォッチリスト | 問い合わせない (取得した記事はすべてウォッチ済み) |

- 未ログインのとき、ID が0件のときは問い合わせない。
- 関連記事のウォッチ状態が取れなかったら、関連記事の取得に失敗したときと同じく関連記事を出さない。本文のウォッチ状態が取れなかったら、ページのエラーにする (今と同じ)。

## 一覧が持つウォッチ状態

- ダッシュボードとウォッチリストの一覧 (`LoadMoreArticleList`) は、表示している記事のうちウォッチ済みの ID を自分で持つ。最初の24件の分はサーバーから一度だけ受け取り、「さらに読み込む」で足した分は `loadMoreArticles` / `loadMoreWatchlist` の戻り値から足す。
- `WatchlistButton` は、追加・解除が成功したら `onWatchedChange` で知らせる。一覧はそれを受けて自分の集合を更新する。ウォッチリストで解除した記事が一覧から消えるのも、この集合による。
- 記事詳細の本文と関連記事は、操作のあとにサーバーが描き直す値を使い、知らせは受けない。
- 別のページでウォッチを操作してから戻ると、Next は保っていた一覧を捨て、サーバーから最初の24件で描き直す (#548 から)。何もせずに戻ったときは、一覧もその状態もそのまま残る。どちらの場合も画面をまたいで状態を持つ必要はないので、持たない。
- 別のタブ・端末での変更は、その一覧が画面にある間は反映されない。

## 不変条件

- 記事一覧・記事詳細・関連記事の応答はユーザーに依存しない (ウォッチ状態を含めない)。
- 問い合わせは本人のウォッチだけを返す。
- 本文のウォッチボタンの表示は、関連記事の取得を待たない。
- 失敗した操作は、一覧の状態を変えない。

## 破壊的変更

- `articleIds` を必須にする。frontend と同じ PR で反映する。
- rollout 中の数分間は、古い frontend が `articleIds` なしで呼んで 422 になり、ログイン中のダッシュボードと記事詳細がエラーになる。これは許容する。
- 新しい frontend と古い backend の組み合わせでは、古い backend が `articleIds` を無視して全件を返すので、表示は正しい。

## frontend の境界

- `features/news` から `features/watchlist` への一方向の例外に、`@/features/watchlist/server` を加える。`loadMoreArticles` が、足した記事のウォッチ状態を取るため。

## 対象外

- 別のページで操作して戻ったときに、読み込んだ続きを残すこと。残すには、記事の保持・スクロール位置・ウォッチ状態を画面の外で持つ設計が必要になる。
- 別のタブ・端末での変更の反映。
- `/me/watchlist`・記事 API・キャッシュ戦略の変更、ウォッチ用の索引、e2e の追加。
