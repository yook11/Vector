# 項目別サニタイズのログポリシー

作成: 2026-09-23
Status: Partially implemented
Implementation: 項目全体のマスク・サニタイズ共通入口・ポリシーからの接続を実装済み。全文字列処理の責務整理と最初の対応 (`canonical_url`・`source_url` → `sanitize_article_url`) は[ログの情報漏洩防止と項目別サニタイズの責務分離](./logging-leak-prevention-policy.md)で実装済み。実際の共通・目的別項目の選定は未実施。

[共通基底ポリシー](./logging-base-policy.md)へ項目別サニタイズを追加する差分仕様。項目別サニタイズの契約は本書を優先する。既存の全文字列処理は今回維持し、情報漏えい対策としての整理は別タスクで行う。

変更状況: 全文字列処理の整理とサニタイズの定義・対象は[ログの情報漏洩防止と項目別サニタイズの責務分離](./logging-leak-prevention-policy.md)を優先する。本書の `connection_url` / `upstream_message` の対応、`mask_assignments` の扱い、テスト配置の記述は同書で置き換える。

## Problem

出力対象の全文字列に同じ秘密情報検出を適用しており、どの項目の何を隠したいかがポリシーに表れていない。共通の出力準備と、項目に応じた部分的な秘匿を分離する。

## Evidence

- [base.py](../../backend/app/log_policy/base.py): `LogPolicyRules` は `allow / deny / mask / sanitize` を保持する。
- [value_preparation.py](../../backend/app/log_policy/value_preparation.py): マスク・構造検査後に項目別サニタイズを適用し、文字列と辞書キーへの既存の `sanitize_text → mask_assignments` も維持する。
- [processor.py](../../backend/app/log_policy/processor.py)・[diagnostics.py](../../backend/app/log_policy/diagnostics.py): 通常項目・抽出した例外・入力由来の診断に保護処理を適用する。
- [既存テスト](../../backend/tests/log_policy/): 形式別の秘匿、構造検査、マスク、最終出力の保証を持つ。今回の契約に関係する箇所だけを追加・更新する。

## ポリシーの契約

| 規則 | 責務 |
| --- | --- |
| `allow` | トップレベルの項目を出力対象にする。 |
| `deny` | 項目を値ごと除外する。ネストにも適用する。 |
| `mask` | 指定した項目名を残し、値全体を `***` に置き換える。値の型や内部構造は検査しない。 |
| `sanitize` | サニタイズ対象の項目名を指定する。 |

マスク対象の項目は、項目名・項目数の検査と `deny` による除外、トップレベルの `allow` 選別を通った後、値の検査・再帰へ進む前に固定マーカーへ置き換える。辞書や配列も全体を一つの `***` に置き換え、内部の文字数・項目数は走査しない。置換後のマーカーはサニタイズなどの文字列加工へ渡さない。

文字列中の `key=value` を探す既存の `mask_assignments()` は、項目全体のマスクとは別の漏えい防止処理として整理する。今回の実装では既存の呼び出しを維持しており、ポリシーの `mask` 集合との切り離しは別タスクで行う。

ポリシーの `sanitize` は項目名の集合とし、呼び出す関数は保持しない。`sanitize.py` が「項目名 → 対応する処理」の対応表を所有し、共通入口 `sanitize_field_value(field_name, value)` で処理を選ぶ。ポリシーが適用対象を選び、サニタイズ側が値の検査・検出・置換を担当する。

- 項目名は既存の `normalize_key` で正規化して完全一致で照合する。未登録項目へ項目別サニタイズを適用しない。既存の全文字列処理は未登録項目にも適用する。
- 登録項目の子を持たない値は、対応する処理が期待する型か確認してから渡す。現在の入力契約は `str` とし、数値など型が合わない値はその部分を `[unsupported]` に置き換える。
- 対応する処理を適用し、形式に該当する部分がなければ値を変更しない。複数の形式を扱う処理の合成と順序も `sanitize.py` が所有する。サニタイズ未指定でも共通の構造検査とマスクは適用する。
- `sanitize` の登録は出力許可を与えない。`allow` と併用でき、`deny` に該当する項目は値の処理前に除外する。`allow` と `deny` の重なりは、基底どおり実行時に `deny` を優先する。
- 基底ルールを必ず含め、`extend()` は親のサニタイズ対象を削除せず追加する。基底・親・子で同じ項目を指定しても対象は重複しない。完成済みの規則は構築時に確定する。

## ネストと責務

- 辞書は各階層の項目名で同じ規則を選ぶ。親項目の処理を辞書内の全値へ広げない。
- 対象項目の配列では、子を持たない各要素に同じ型確認とサニタイズを適用する。配列の入れ子では規則を引き継ぎ、辞書に入ったら子の項目名で選び直す。
- 数値などの非文字列をサニタイズのために文字列化しない。未登録項目の値は共通の構造検査に従って型を維持し、共通処理が生成した固定マーカーは型確認・検出・置換の対象にしない。
- 実際に出力する共通項目は共通ポリシー、目的固有の項目は目的別ポリシーで指定する。今回の接続では具体的な登録項目を追加せず、基底の `sanitize` は空とする。
- 形式別の処理は既存の `sanitize.py` を再利用する。自由文全体から秘密情報を検出する処理は、項目別サニタイズとは別の情報漏えい対策として整理する。

`LogPolicyProcessor` は完成済みの規則を渡し、`LogValuePreparer` は構造検査・再帰・共通のマスクを担当する。サニタイズ対象では項目名と値を `sanitize.py` の共通入口に渡し、共通入口が対応する処理の選択・入力型の確認・処理結果の返却を担当する。型不一致と正常時の戻り値はサニタイズ側の単体テストで確認し、ネストした値からの呼び出しはプロセッサー側のテストで確認する。項目ごとの保護判断をログ呼び出し側へ分散させない。

今回のテストで扱う対応は `connection_url → sanitize_url_userinfo`、`upstream_message → sanitize_jwts` とする。実際に出力する共通・目的別項目の対応表は、後続タスクで確定する。

`test_sanitize.py` は共通入口へ項目名と値を渡したときの戻り値を検証する。形式別の検出境界は `test_sanitize_url.py`・`test_sanitize_jwt.py`・`test_sanitize_aws.py` に置き、秘密鍵・プロバイダートークンなどと自由文サニタイズの既存テストは `test_sanitize_other.py` にまとめる。

## Invariants

- 項目の選別後、マスク対象なら値の処理を終了し、対象外だけ構造・予算検査と登録されたサニタイズへ進む。文字列内部の検出処理の順序は、別タスクで整理するまで現行を維持する。
- 共通の型・深さ・文字数・件数・循環参照・非有限数の検査、除外値を検査しない振る舞い、配列の順序は維持し、登録項目にはサニタイズの入力型確認を追加する。
- 内容の書き換えは指定された秘匿処理に限定し、一律の空白除去や改行削除を追加しない。出力形式のエスケープは renderer が担当する。
- bind・contextvars・ログ引数・抽出例外に同じ完成済みの規則を使い、ログ入力から規則を変更できない。
- 必要な診断情報を残し、処理失敗時に原文を出さない。業務結果・例外伝播・再試行を変更しない。

## 後続タスクで具体化する事項

既存の出力項目について「出所・値の制約・必要なサニタイズ・共通／目的別の所有先」を一覧化する。今回の接続の前提にはしない。

`event`、通常・ネストした例外文、`error_details`、診断項目、入力由来の辞書キーを確認する。項目の値に対する `sanitize` の登録だけでは、辞書キー自体は保護されない。動的キーの出力契約と保護方法もこの段階で確定し、未解決の経路があるまま一律サニタイズを外さない。

## Non-goals

- `allow / deny` の意味、例外情報の抽出契約、業務処理の変更。
- 実際の共通・目的別項目の選定、文字列内部の漏えい検出処理の再設計。
- 秘密形式の検出パターン追加、汎用パス指定言語、新規依存の導入。
- 未接続ロガーの一括移行、Logfire・監査DB・デプロイログの変更、AWSへの適用。

## 実装ステップ

各実装ステップで必要な振る舞いのテストを先に書き、失敗を確認してから実装する。既存の検証を再利用し、異なる条件は独立して読めるケースにする。

| Step | 成果 | 主な検証 |
| --- | --- | --- |
| 1 | `LogPolicyRules` に `sanitize` と継承・正規化を追加する。 | 親の対象項目の維持、項目の重複排除、出力許可との独立、構築後の規則の保護。 |
| 2 | `sanitize.py` に項目名から処理を選ぶ共通入口を置く。 | 型不一致の固定マーカーと、対応する処理の戻り値。 |
| 3 | プロセッサーから規則を渡し、マスク後の値の準備処理へ共通入口を接続する。 | 辞書・配列の再帰、項目名の正規化、型不一致、マスク対象の処理終了、最終JSON出力と既存の上限・失敗時契約。`/check` で検証する。 |
| 後続 | 実際の登録項目を選び、全文字列処理を情報漏えい対策として整理する。 | 診断・例外・動的キーを含む保護を維持し、目的別仕様と同期する。 |

## Done（今回の接続）

- サニタイズ対象がポリシーから、各項目に対応する処理が `sanitize.py` から読み取れ、未指定項目へ項目別処理を適用しない。
- 親の規則、ネスト・例外・診断・動的キーの保護、共通の整形とマスクを検証できている。
- 最終出力に保護対象が残らず、必要な診断が残ることをテストで確認できている。
- 関連仕様と実装状態を同期し、未実行の検証があれば理由を明記している。
