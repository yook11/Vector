# URL・JWTサニタイズの修正と性能測定（2026-09-18）

この記録と測定JSONは入力上限導入前の結果を保存している。その後、単一4000文字・イベント合計16000文字・走査128件を採用した（[現行の契約](./logging-base-policy.md#入力上限と置換単位)）。現在のスクリプトを再実行すると、processor測定には上限超過による項目置換も含まれるため、過去のprocessor時間と同じ処理内容とは限らない。

## 変更と検証範囲

- URLは `://` から候補を探す方式を維持し、隣接する数字・記号の後ろのschemeも検出する。旧IGNORECASEで認識していたUnicodeの4文字も維持する。
- JWTはbase64urlの区画を一度ずつ走査し、連続する3区画で既存形式を判定する。header内部のeyJから始まる検出と、置換済み区画を再利用しない動作を維持する。
- 入力長上限・切り詰め・フィールド全体のlimit置換は今回変更していない。以下の上限は次の実装に向けた候補である。

## 測定方法

- Python 3.13.11 / Darwin arm64 のローカル環境。実ログ・秘密情報・外部サービスは使用していない。
- ウォームアップ後、3呼び出しの平均経過時間を7バッチ測定し、その中央値を記載する。旧正規表現の比較だけは1バッチ1呼び出し。CPU時間そのものやp95/p99、ハードな最大実行時間ではない。
- 他のテスト実行と重ならない状態で測定したが、OSスケジューリング等の影響は残る。バッチ平均の最大値も生データに記録する。
- 単一文字列は9種類。英字列、JWT接頭辞の繰り返し、長い2区画候補、短いJWTの連続、公開URL、長いscheme、非禁止キー付き値、引用符を含む秘密値、日本語を測った。
- processorは通常値の保護までを測る。JSON renderer・stdout・CloudWatch配送は含まない。現行の500文字切り詰めは残るが、入力全文のサニタイズは実行される。
- イベントの総文字数は、event文字列・ネスト内のキー名・文字列値の合計。合計を固定し、1 / 16 / 128 / 512 / 900項目へ配分する。トップレベルの固定キー名とポリシー識別子は含まない。
- 例外固有の抽出、将来の事前走査やフィールド単位の全置換のコストは未測定。

## 上限の提案（未適用）

測定した範囲で「文字列単体は約1ms、通常値のイベント処理は約2ms以内を目安にする」という設計目標を仮置きする場合、次の組合せを候補とする。既存の500文字やSafeUrlの2,048文字から導いた値ではない。

| 制約 | 候補 | 測定上の根拠 |
| --- | ---: | --- |
| サニタイズ前の単一文字列 | 8,192文字 | 短いJWTが密集するケースでも約0.78ms。16,384文字では約1.53ms。 |
| サニタイズ対象のイベント内合計 | 16,384文字 | 128項目までの測定では約1.86ms。32,768文字では約3.29ms。 |
| イベント全体で走査する値・コンテナ | 128件 | 同じ合計文字数でも多数項目では固定費が増すため、文字数だけで処理量を制限できない。 |

- 上記は採用済み仕様でも実行時間保証でもない。約2ms/eventという目標自体も提案であり、本番のCPU・ログ頻度・必要な診断情報で検証する。
- 128項目の測定はネストの辞書自体やeventを含めると128ノードを超えるため、候補の走査128件を完全に同一条件で再現した測定ではない。任意の深さ・型の組合せも未網羅。
- 将来の合計文字数には通常値だけでなくキー・event・例外文・型名・frame文字列も含める。denyで除外した値はサニタイズ対象外だが、除外する項目の走査は件数に数える。
- 1文字列の上限内でも、多数の値があると全体の予算を超える。URLを予算から除外しない。
- 事前判定で超過したトップレベルフィールド全体を固定値に置換する方針は別途実装する。先に原文を切ってからサニタイズする方式にはしない。
- 最終JSONのバイト数制限は別の出力制約である。今回の計測・候補だけでは整数やエスケープを含むイベント全体のサイズ保証にはならない。
- 高頻度ログでは2msも無視できないため、ログ発生頻度が未確認の状態で「CPU負荷として安全」とは断定しない。
