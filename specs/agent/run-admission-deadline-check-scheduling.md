# run受付時の期限確認タスクの予約

Status: Implemented
Updated: 2026-09-07
Scope: run受付のDBコミット後に、元のdeadline_atを基準とした単発の期限確認タスクを予約する

本書はrun受付後の補助的な期限確認予約の契約を定める。「受付」は質問とqueued runのDB確定を指し、ワーカー開始や回答生成開始とは区別する。

## Problem

受付済みrunを元の60秒期限付近で個別に確認し、回収条件を満たす場合に終了させる。
ワーカーがまだ実行を開始していないqueued runにも確認の機会を設ける。
予約漏れ・実行遅延の救済として既存の定期回収を維持し、その条件・頻度は変更しない。

## 受付から予約までの順序

対象は`POST /api/v1/research/responses`による新しいrunの受付とする。
新規スレッドへの質問と、既存スレッドへの追加質問の両方に適用する。

1. 既存の認証・所有権・active run・quota条件に従ってrunを作成する。
2. 質問、run、quota予約をDBにコミットする。
3. 回答実行タスクを投入する。
4. FastAPIの`BackgroundTasks`へrun IDと確定済みの`deadline_at`を渡し、既存の受付レスポンスを送信する。
5. HTTPレスポンス送信後、バックグラウンドで対象runの期限確認タスクを予約する。

予約操作はバックグラウンド内で最大2秒、再試行なしとする。回答開始・HTTPレスポンス送信は予約を待たない。
リクエスト用DBセッションやORMオブジェクトは渡さず、予約のためのDB問い合わせ・トランザクションを追加しない。
受付の拒否・ロールバック・コミット失敗時は、期限確認も回答実行も投入しない。

## Invariants

### 1. DBに確定した期限を予約に使う

- 元の期限は受付時の`deadline_at`とし、予約時・ワーカー開始時の現在時刻から60秒を加算し直さない。
- run作成時に保存した期限値を内部の作成結果で返すなど、DBへ記録した値を予約処理へ渡す。
- `CreatedAgentRun`など内部契約の拡張は可能だが、公開APIへ期限・予約状態を追加しない。
- 予約に使うために`deadline_at`を変更しない。
- 予約時刻はtimezone付きのUTCとして扱う。

### 2. 予約時刻だけを秒単位で切り上げる

```text
scheduled_at = deadline_atを次の秒境界へ切り上げた時刻
```

| DB上のdeadline_at | 予約時刻 |
|---|---|
| 12:01:00.000000 | 12:01:00.000000 |
| 12:01:00.000001 | 12:01:01.000000 |
| 12:01:00.350000 | 12:01:01.000000 |
| 12:01:59.999999 | 12:02:00.000000 |

- 秒境界ちょうどの値はそのまま使う。固定の2秒などを追加しない。
- 切り上げは分単位ではなく秒単位とし、日付をまたぐ場合も同じ規則を適用する。
- 実際の回収判定には丸める前のDB上の期限を使う。
- 予約時に現在時刻を取得・比較しない。登録が遅れて予定時刻を過ぎても、同じ単発予約経路へ渡す。
- 予約登録・キュー待機・ワーカー稼働による遅延は許容する。ミリ秒単位や予定時刻ちょうどの実行は保証しない。

### 3. 予約タスクは対象runの最新状態を確認する

- タスクの対象は受付済みの`run_id`一つとする。他runやスレッド全体の回収を実行しない。
- 受付時の`attempt_epoch`に固定しない。queuedからrunningへ進んだrunも確認対象とする。
- runの状態・開始記録・期限・所有者・quota情報は実行時にDBから取得する。
- 予約時の状態や時刻を根拠に、そのまま`deadline_exceeded`を書き込まない。
- タスクは信頼されたバックエンドの受付経路から投入し、任意runを回収する公開endpointは追加しない。

回収条件は[回答生成の期限契約](./answer-generation-deadline.md)と既存の定期回収に揃える。

| 実行時のDB状態 | 動作 |
|---|---|
| queued、または回答生成未開始のrunning | `DB現在時刻 >= deadline_at`の場合だけ回収 |
| 回答生成開始済みのrunning | `DB現在時刻 >= answer_started_at + 工程制限時間 + 猶予`の場合だけ回収 |
| それぞれの期限より前 | 変更せず終了 |
| 終了済み・削除済み | 変更せず終了 |

例えば55秒で回答生成が始まり、元の60秒の予約タスクが実行された場合、新しい回収期限より前なら
runを終了させない。このタスクから回答生成後の期限へ再予約する処理は、本スライスに含めない。
新しい期限まで残るrunは、既存の定期回収とスレッド表示時の確認で救済する。

予約タスクが早く到着した場合も、期限前のrunは終了させない。タスク内で期限までsleepしたり、
独自の待機ループを回したりしない。

### 4. 終了の確定は共通の回収契約に従う

- 候補取得・更新をrun IDで限定し、定期回収と同じ期限判定を再利用する。
- 対象runのロック取得後、最新の状態・実行世代・開始記録とDB時刻で回収条件を確認する。
- 読み取った現在の状態と実行世代に対して更新し、待機中に変化した前提を再判定する。
- 生成開始・保存・失敗・キャンセル・他の回収が先に確定した場合、その最新状態に従う。
- 回収時は`deadline_exceeded`、`assistant_message_id=None`、`error_code=None`とする。
- 開始時刻・元の期限・実行世代・履歴・handoffは変更しない。
- queuedのquota返却は既存条件に従い、run終了と同じトランザクションで行う。runningは返却しない。
- legacy runとquota counter不整合の扱いも既存回収に揃える。
- runningの回収後は、DBコミット後に既存の終了通知をbest-effortで送る。
- 通知・観測の失敗でDBの終了を取り消さない。重複実行で終了更新・quota返却を繰り返さない。

### 5. 予約と実行の失敗を回答実行から分ける

| 事象 | 扱い |
|---|---|
| 予約登録の通常例外やタイムアウト | 安全なログを記録して終了。run・quota・送信済みレスポンスは変更しない |
| 予約の応答が不明で、実際には登録されている可能性がある | 予約を再試行しない。重複が発生しても回収処理を冪等にする |
| DB受付commit後、予約前にプロセス停止 | 予約漏れを許容し、定期回収とスレッド表示時の回収で救済する |
| 回答実行タスクの投入が失敗 | 既存のenqueue失敗処理に従う。期限確認タスクは実行時に状態を再確認する |
| 期限確認タスクのDB処理・commitが失敗 | ロールバックしてタスク失敗として記録する。既存の定期回収で救済する |
| scheduler・worker停止、キュー滞留 | 復旧後は最新状態で確認する。遅延を理由に期限を延長しない |

予約失敗だけを理由に受付を503へ変更したり、受付済みrunを`failed`にしたり、quotaを返却したりしない。
回答実行タスク自体の投入失敗や受付処理のキャンセルは、予約失敗として握りつぶさない。
本スライスでは独自の無制限retryやDBとキューを原子的にする新しい仕組みを追加しない。

### 6. 予約の寿命と負荷

- 予約はrunごとの単発とし、定期的な繰り返し予約にしない。
- APIまたは回答ワーカーのメモリ内タイマーだけに依存せず、プロセス停止後も予約が残る方式を使う。
- 正常完了・キャンセル時の予約取消は必須にしない。残った予約は終了済みrunを確認して終了する。
- 予約基盤の処理済み単発予約の削除・消費動作を確認し、完了した予約を蓄積し続けない。
- タスクpayloadに質問・回答・認証情報を含めない。payloadはrun IDのみとする。
- 定期回収の既存schedule、生成中の継続確認頻度、スレッド表示時の回収契約は変更しない。

## 採用した予約基盤

- 既存依存の`ListRedisScheduleSource`を使い、API・agent schedulerで専用prefix `vector-agent-deadline`を共有する。
- 小さなアダプターで予約本体と時刻索引への登録をRedisの`MULTI/EXEC`へまとめ、接続poolの終了処理を補う。
- JSON形式で保存し、日時はtimezone付きISO形式とする。
- 既存のRedis接続・IAM認証設定を継承する。APIとschedulerはプロセスごとに接続を所有し、終了時に解放する。
- `skip_past_schedules=False`により、登録遅延や再起動後も過去の予約を取得する。送信後の単発予約削除はsourceの既存処理を使う。
- agent schedulerの予約一覧更新のみ1秒間隔とする。他schedulerの60秒間隔と、毎分のDB定期回収は維持する。
- バックグラウンド予約全体は2秒で打ち切る。Redis接続・socket・pool待機にも2秒を設定するが、各待機を合計して上限を延ばさない。
- 予約確認タスクは独自の再試行・再予約を行わない。プロセス停止による予約漏れ・送信漏れは既存の回収経路で救済する。

## Non-goals

- 回答生成開始時の追加予約、初回予約から新しい回収期限への再予約。
- 定期回収の廃止・頻度調整、継続確認の頻度調整。
- 期限や生成タイマー・回収猶予の変更、handoffの非同期化。
- 予約時刻ぴったりの実行保証、予約漏れを完全になくすoutboxなどの導入。
- 正常終了時の予約取消、新しい公開API・予約状態UIの追加。
- 認証・所有権・quotaポリシーの変更。

| queuedの期限到達 | 対象runだけ回収し、対象ならquotaを一度返却 |
| queuedからrunningへ世代が進行 | 受付時の世代に固定せず、現在のrunを判定 |
| 55秒で生成開始、60秒付近で確認 | 新しい回収期限より前なら維持。追加予約はしない |
| 遅延実行時に生成後の回収期限へ到達 | 共通条件に従って回収 |
| 期限前の早着・終了済み・削除済み | 状態を変更せず終了 |
| 重複実行、保存・開始・キャンセル・定期回収との競合 | 終了状態とquotaを二重更新せず、最新状態を維持 |
| DB失敗・終了通知失敗 | DB失敗はrollback、通知失敗はcommit済み状態を維持 |
| 予約元プロセス停止・scheduler再起動 | 予約がメモリだけに依存せず、期限到達済み予約の動作が確認できる |

## Done

- 予約基盤と短い待機上限を確定し、上記の受付順序・失敗時の振る舞いを実装する。
- DB期限を秒単位に切り上げ、run単位の単発確認を予約できる。
- 確認タスクが共通の回収条件・quota・終了通知・競合保護に従う。

- 受け入れ条件と予約基盤の動作を検証し、`/check`の結果と実装への参照を記録する。
