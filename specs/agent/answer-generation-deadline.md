# 回答生成の開始期限・回答確定・未完了runの回収

Status: Draft
Updated: 2026-09-05
Scope: Direct Answer / Evidence Answerに共通する、回答生成開始から回答確定または終了までの時間・状態契約

本書の振る舞いは合意済みである。回収猶予の具体値を確定するまでDraftとする。
`answer_started_at`のschema基盤と、初回の回答生成へ進入する際の開始記録を先行実装した。
再生成、開始後の継続・保存、定期回収の判定は未実装である。

## Problem

受付から60秒の期限内に回答生成を開始したrunは、回答生成工程の制限時間を守って得られた回答を、
元の60秒を超えても確定できるようにする。同時に、再試行による時間制限の延長、終了済みrunの
上書き、ワーカー停止による未完了runの放置を防ぐ。

## 時間と用語

| 項目 | 定義 |
|---|---|
| 受付時刻 | runの`created_at`。キュー待機を含む時間の起点 |
| 開始期限 | `deadline_at = created_at + 60秒`。run作成時に固定する |
| 回答生成工程 | 最初の回答生成と、その工程内で許可された再生成を含む一連の処理 |
| 工程の制限時間 | 15秒。再生成を含めた工程全体の制限 |
| 回答生成開始時刻 | `answer_started_at`。工程への最初の進入をDBに確定した時刻 |
| 回収猶予 | 生成終了から回答の保存までを考慮した追加時間。生成の持ち時間には含めない |
| 回収期限 | `answer_started_at + 工程の制限時間 + 回収猶予` |
| 回答確定 | 回答の保存とrunの`completed`への遷移が、同じトランザクションでコミットされた状態 |

DBの時刻を、開始可否・開始時刻の記録・保存可否・回収の判定の正本とする。
期限は`now < 期限`の場合だけ有効とし、境界時刻ちょうどは期限切れとする。
ロック待機を伴う判定では、ロック取得後のDB時刻を使う。

工程の制限時間は、生成処理のタイマーとDB側の回収条件が同じ定義を参照する。
回収側に独立した`15秒`や、計算済みの合計秒数をハードコードしない。回収猶予は別に定義する。

## Invariants

### 1. 条件を満たした開始だけをDBに記録する

工程を最初に開始するとき、次の条件を同じトランザクションで確認する。

- runが`running`である。
- ワーカーの`attempt_epoch`が、DBに記録された現在の実行世代と一致する。
- DB現在時刻が`deadline_at`より前である。
- `answer_started_at`が未記録である。

条件をすべて満たした場合だけ、DB時刻で`answer_started_at`を記録する。
記録をコミットできた場合だけ回答生成を始める。書き込み失敗・ロールバック・状態競合時には開始しない。
時刻の記録と開始可否の確認を、別々のトランザクションに分離しない。

実行中かつ現在の実行世代であっても、開始期限に達している場合は回答生成を開始せず、
`deadline_exceeded`へ遷移する。終了済みまたは古い実行世代の場合は、状態を変更せず停止する。

### 2. 再生成にも開始期限を適用する

- 工程内の2回目以降の生成も、開始直前に実行中・実行世代一致・開始期限内であることを確認する。
- 元の60秒に達した後は、最初の生成が期限内に始まっていても、新しい生成を開始しない。
- 再生成を開始できない原因が開始期限への到達であれば、`deadline_exceeded`とする。
- 再生成で`answer_started_at`を更新しない。工程の15秒タイマーもリセットしない。
- 工程内の生成回数と、ワーカーの所有権を表す`attempt_epoch`は別の概念として扱う。
- タスクの再配送・再実行を、記録済みの回答生成工程を新しい予算で開始し直す権利として扱わない。

開始条件を満たすことは、無条件に再生成を許可する意味ではない。再生成可能な失敗の種類・回数は、
回答生成工程の再試行ポリシーにも従う。

### 3. 開始済みの生成は元の60秒だけでは中断しない

- 期限内に開始した個々の生成は、元の60秒を超えても継続できる。
- ストリームの断片受信時や生成終了時の継続確認で、元の60秒超過だけを理由に停止しない。
- 工程全体の15秒制限は維持する。超過した場合は工程の失敗として扱い、回答を採用しない。
- 実行中でなくなった場合や実行世代が一致しなくなった場合は、継続・保存の権利を失う。
- 回収猶予や定期回収の遅延を、生成工程の延長に使わない。

### 4. 回答は最初の保存トランザクションで確定する

回答生成工程を正常に完了した回答について、保存時に次の条件を確認する。

- runが`running`である。
- 保存するワーカーの`attempt_epoch`が現在の実行世代と一致する。
- 当該工程の`answer_started_at`がDBに確定している。
- ロック取得後のDB現在時刻が回収期限より前である。

元の`deadline_at`を超えていることは、保存を拒否する理由にしない。
条件を確認したトランザクションで回答と関連データを保存し、runを`completed`にする。
コミット前の生成結果や配信済みの部分回答を、確定した回答として扱わない。

保存トランザクションは再試行しない。保存に失敗した場合は、実行中かつ現在の実行世代であることを
条件に`failed`を確定する。元の60秒超過を理由に、その保存失敗を`deadline_exceeded`へ分類し直さない。
失敗状態の永続化もできなかった場合は、DBに残った未完了runを定期回収の対象とする。

定期回収がまだ実行されていなくても、保存可否の判定時に回収期限へ達している場合は回答を保存せず、
`deadline_exceeded`へ遷移する。

### 5. 定期回収は開始記録によって条件を分ける

| 未終了runの状態 | 回収条件 | 終了状態 |
|---|---|---|
| 回答生成開始時刻がない | `DB現在時刻 >= deadline_at` | `deadline_exceeded` |
| 回答生成開始時刻がある | `DB現在時刻 >= answer_started_at + 工程の制限時間 + 回収猶予` | `deadline_exceeded` |

開始記録があるrunを、元の60秒だけで回収しない。開始時刻を記録した直後、生成途中、生成終了後、
保存失敗後のいずれでワーカーが停止しても、同じ回収条件を適用する。

回収期限は「回収対象になる時刻」であり、その瞬間に定期処理が動くことを保証しない。
実際の終了確定は、期限以降の回収処理がDB更新をコミットした時点である。

### 6. 終了状態は終了原因で決め、確定後は上書きしない

| 終了原因 | 終了状態 |
|---|---|
| 初回・再生成の開始時に開始期限へ到達 | `deadline_exceeded` |
| 回答生成工程の15秒タイムアウト | `failed` |
| 回答生成工程の最終的な失敗 | `failed` |
| 回答保存の失敗 | `failed` |
| 未完了runの回収期限への到達による終了 | `deadline_exceeded` |
| 正常な回答保存のコミット | `completed` |

生成・保存の失敗は、元の60秒を超えた後に起きても`failed`とする。
工程内で再試行可能な失敗は、その時点では最終的な失敗ではない。続く生成の開始を期限が阻んだ場合は
`deadline_exceeded`となる。

`attempt_epoch`による実行世代の確認と、`running`という状態条件の両方で更新を保護する。
保存・失敗処理・キャンセル・回収が競合しても、先に確定した終了状態を維持する。
古いワーカーや遅れて到着した結果は、終了済みrunを上書きしない。

## Verification — 受け入れ条件

以下の秒数はrun受付からの経過時間である。成功例は、保存時に実行中・実行世代一致・回収期限前という
条件を満たすことを前提とする。

| ケース | 期待する結果 |
|---|---|
| 55秒で生成開始、67秒で正常な回答を生成・保存 | `completed` |
| 60秒ちょうど、または60秒経過後に初回生成を開始しようとする | 生成を呼ばず`deadline_exceeded`。開始時刻を記録しない |
| 55秒で初回生成開始、58秒で許可された再生成を開始 | 開始可能。開始時刻と工程タイマーは55秒起点のまま |
| 55秒で初回生成開始、62秒で再生成を開始しようとする | 再生成を呼ばず`deadline_exceeded` |
| 55秒で工程開始、70秒で工程の15秒タイムアウト | `failed`。回答を採用しない |
| 55秒で工程開始、67秒で生成が最終的に失敗 | `failed` |
| 期限内に開始した生成が成功し、60秒経過後に保存が失敗 | 保存を再試行せず`failed` |
| 開始記録のトランザクションがロールバック | 回答生成を呼ばない |
| 開始判定のロック待機中に60秒へ到達 | ロック取得後の時刻で拒否する |
| 回収期限より前の開始済みrunを、元の60秒経過後に回収処理が確認 | 終了させない |
| ワーカー停止後、開始時刻から工程制限時間＋猶予が経過 | 次の回収処理で`deadline_exceeded` |
| 保存可否の判定時刻が回収期限ちょうど | 回収処理の実行有無にかかわらず回答を拒否し`deadline_exceeded` |
| 保存と回収・キャンセル・失敗処理が競合 | 終了状態は一度だけ確定。回答の部分保存を残さない |
| 古い`attempt_epoch`で開始・保存・失敗更新を試みる | 現在のrunを変更しない |
| 再生成・再配送・再実行で開始時刻の再設定を試みる | 工程の制限時間と回収期限を延長しない |

Direct AnswerとEvidence Answerの両方で、生成開始・再生成・工程タイムアウトの条件を検証する。
時間境界は実時間の60秒待機に依存せず検証し、開始と回収、保存と回収のDB競合も確認する。

## 実装前に確定する値

回収猶予の具体的な秒数。生成終了後の処理と保存時のロック待機を考慮して定める。
保存時のロック待機上限は確認時点で10秒である。猶予を15秒とする案はあるが、本書では確定値として扱わない。
猶予は未完了runを回収するための時間であり、保存成功やschedulerの稼働を保証するものではない。

## Implementation

- `agent_runs.answer_started_at`を、timezone付き・nullable・defaultなしの列として追加するexpand migrationを実装した。
- ORMにも同じ列契約を追加した。公開APIへの露出は行わない。
- migrationのupgrade・downgrade・再upgradeで、既存runの他の列とデータを維持する契約を検証する。
- Alembic headは`z20_agent_run_answer_started_at`の1本で、migration gateはexpandとして受理した。
- 初回生成の開始時にrunをロックし、ロック取得後のDB時刻で`running`、`attempt_epoch`、
  `answer_started_at IS NULL`、`now < deadline_at`を同じトランザクション内で確認する。
- 開始条件を満たす場合だけ`answer_started_at`を記録し、開始期限ちょうど以降は回答生成を呼ばず
  `deadline_exceeded`へ遷移する。終了済み、古い実行世代、開始記録済み、存在しないrunは変更しない。
- Queue taskはrunと実行世代に固定した短命トランザクションの開始依存を、Direct Answerと
  Evidence Answerに共通する`AnsweringRunner`へ必須で渡す。commit後だけ回答生成へ進む。

- 開始拒否・DB例外時にanswererを呼ばないこと、ロールバックで開始時刻が残らないこと、
